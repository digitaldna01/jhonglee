### 아이디어

반도체·디스플레이 공장은 MES(Manufacturing Execution System) 위에서 돌아가요. 그런데
대부분의 MES 화면은 정보가 빽빽하고 시각적으로 무거운, 전형적인 "엔터프라이즈 소프트웨어"예요.
그래서 궁금했어요. 공장 제어 인터페이스를 잘 만든 B2B SaaS 제품처럼 디자인하면 어떤 모습일까?

컨셉은 **FabOS**, 디스플레이 패널 생산을 위한 스마트 팩토리 인텔리전스 플랫폼이에요. 캔버스
하나에 핵심 패널 세 개를 얹었어요.

- 중앙엔 인터랙티브 **공정 맵**: 유리 기판 투입 → 세정 → 증착 → 노광 → 검사 → 셀 조립 → QC
- 왼쪽엔 드래그할 수 있는 **AI 에이전트 / 워크플로우 패널**
- 오른쪽엔 에이전트 실행 일정을 관리하는 **Notion 스타일 일정 캘린더**

시각 레퍼런스는 항공 화물 대시보드와 클린룸 제어 패널에서 가져왔어요. 밝은 회색 배경, 둥근
카드, pill 탭, 최소한의 검정 포인트. 산업적이면서도 차분한 인상이 목표였어요.

</Lang>

<Lang locale="en">

### The idea

Modern semiconductor and display fabs run on MES (Manufacturing Execution Systems) — dense, often ugly enterprise software. I wanted to explore what a premium, calm, SaaS-quality factory control interface could look like if you designed it the way you'd design a great B2B product.

The concept: **FabOS** — a smart factory intelligence platform for display panel production. Three panels, one canvas:

- A central interactive **process map** (glass substrate → cleaning → deposition → lithography → inspection → cell assembly → QC)
- A left **AI agent / workflow panel** with draggable job cards
- A right **Notion-style schedule calendar** for orchestrating agent runs

The visual inspiration came from aircraft freight dashboards and clean-room control panels — light gray backgrounds, rounded cards, pill tabs, minimal black accents. Industrial, but calm.

```text
Fonts: Inter (300/400/500/600) + DM Mono (400/500) via Google Fonts.
Colors: Page bg #F5F5F2, card surface #FFFFFF, primary text #1A1A1A, secondary
#888888. Status — Green #10B981 (pass/run), Amber #F59E0B (hold/warn), Red
#EF4444 (alarm/fault), Blue #3B82F6 (processing/info). Violet #7C3AED reserved
exclusively for AI agents and orchestration.

Style rules: No dark backgrounds. No gradients. No neon.
Cards use 1px solid #E8E8E4 border, 12–16px radius.
Navigation tabs are black pill (#1A1A1A fill, white text) on off-white page.
All data values (lot IDs, timestamps, sensor readings) use DM Mono.
Section labels are 10px uppercase #888 with 0.1em letter-spacing.
Black fill (#1A1A1A) is reserved for primary action buttons only.
Chips always use: colored dot + pastel background + dark matching text.

Mood: Clean-room precision. Calm, trusted, technical.
Like aircraft avionics — zero noise, total operational clarity.
```

### Step 3 — Generating the dashboard design

With the design system loaded, I prompted Claude Design to generate the three-panel dashboard layout. The key to a good result was being specific about each panel's _behavior_, not just its appearance.

The prompt described:

</Lang>

```text
- 중앙 공정 맵은 정적인 일러스트가 아니라 인터랙티브 운영 캔버스여야 한다. 설비 모듈 선택, lot count badge, alarm chip, status indicator를 포함한다.
```

### Step 4 — 컴포넌트 디테일 다듬기

몇몇 컴포넌트는 손이 더 갔어요.

**Process map modules**
첫 버전의 공정 단계는 라벨 붙은 상자 수준이었어요. 그래서 module마다 status indicator dot,
WIP lot count badge, 은은한 selection highlight가 필요하다고 더 요청했죠. 바이브 디자인 두어
번 만에 공정 모듈이 진짜 설비 cell처럼 느껴지기 시작했어요. 선택할 수 있고, 한눈에 들어오고,
정보는 빽빽한데 어수선하지 않은 모습으로요.

**AI agent cards**
Violet accent의 톤을 잡는 데는 몇 번의 시도가 들었어요. 목표는 AI 카드가 일반 workflow card와
확실히 구분되면서도 전체 light palette를 해치지 않는 것. 결국 부드러운 #EDE9FE 배경, #7C3AED
텍스트, violet left-border accent 조합으로 정리했어요. AI 요소인 건 분명히 드러나는데,
차분함은 그대로예요.

**Schedule calendar**
제일 애먹인 패널은 calendar였어요. 초기 버전은 영락없는 Gantt chart였거든요. grid line을
대부분 걷어내고, time slot의 세로 여백을 늘리고, scheduled workflow를 bar 대신 둥근 card로
바꿨어요. 그제야 Notion Calendar의 event 표현에 가까워졌어요.

</Lang>

<Lang locale="en">

### Step 4 — Iterating on components

A few specific components needed extra passes.

**Process map modules** — The first version rendered process steps as simple labeled boxes. I pushed for more: each module needed a status indicator dot, a WIP lot count badge, and a subtle selection highlight state. After two iterations the modules felt like real equipment cells — selectable, scannable, information-dense without being cluttered.

**AI agent cards** — Getting the violet accent right took a couple of tries. The goal was that violet cards should feel distinctly different from regular workflow cards without breaking the overall light palette. The solution was a soft `#EDE9FE` background with `#7C3AED` text and a violet left-border accent — unmistakably AI, but still calm.

**Schedule calendar** — The hardest panel to get right. Early versions looked like a Gantt chart. The fix was removing most of the grid lines, increasing vertical padding on time slots, and treating each scheduled workflow as a rounded card rather than a bar — much closer to how Notion Calendar handles events.

### 잘 작동했던 점

**Design system notes field가 핵심이었어요.**
Claude Design에서 이것만 잘 잡아 두면 이후의 모든 생성이 처음부터 방향을 제대로 잡고 나와요. 폰트와
컬러를 매번 다시 설명할 필요가 없어요. Claude가 이미 디자인 시스템을 알고 있으니까요.

**Claude Design → Claude Code 핸드오프가 기대보다 매끄러웠어요.**
Export된 design context에 color와 spacing 정보가 충분해서 Claude Code가 찍어야 할 게 별로
없어요. "이렇게 보여야 한다"와 "이걸 코드로 만든다" 사이의 간극이 흔한 Figma-to-developer
핸드오프보다 훨씬 좁게 느껴졌어요.

**긴 프롬프트보다 구체적인 프롬프트가 이겨요.**
분위기만 장황하게 늘어놓은 프롬프트는 애매한 결과가 나오기 십상이에요. 반대로 "공정 모듈을
클릭하면 lot status, active recipe, assigned agent가 담긴 slide-in detail panel이 열린다"처럼
구체적인 interaction을 짧게 말한 프롬프트가 훨씬 좋은 결과를 냈어요.

</Lang>

<Lang locale="en">

### What worked well

**The design system notes field is the real unlock.** Once it's set up correctly, every subsequent generation starts from the right place. You don't re-explain fonts and colors every time — Claude already knows.

**Claude Design → Claude Code handoff is surprisingly tight.** The exported design context carries enough information that Claude Code doesn't have to guess at colors or spacing. The gap between "this is what it should look like" and "this is the code" is much smaller than a traditional Figma-to-developer handoff.

**Specificity beats verbosity.** Long prompts describing the general vibe produce mediocre results. Short, precise prompts describing specific interactions ("clicking a process module shows a slide-in detail panel with lot status, active recipe, and assigned agent") produce good ones.

</Lang>

### 다르게 해보고 싶은 점

지금의 process map은 data-driven이라기보다 아직 그림에 가까워요. 실제 운영에 쓰려면 각
process module의 running, alarm, idle 상태를 MES backend에서 오는 live WebSocket 데이터로
움직이는 구조가 필요할 거예요. 다음에 Claude Code와 다시 붙어 볼 만한 주제죠.

Drag-and-drop scheduling에도 edge case가 남아 있어요. event overlap이나 multi-day workflow
같은 건, 실제 공장 운영자에게 내놓기 전에 product thinking이 좀 더 필요해 보여요.

</Lang>

<Lang locale="en">

### What I'd do differently

The process map is still more illustrative than truly data-driven. In a real implementation you'd want the process module states (running, alarm, idle) driven by live WebSocket data from the MES backend. That's a Claude Code conversation for another day.

The drag-and-drop scheduling also has edge cases — overlapping events, multi-day workflows — that would need more careful product thinking before shipping to actual factory operators.

</Lang>

